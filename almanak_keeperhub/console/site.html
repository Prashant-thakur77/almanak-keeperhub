01 / Hero

Almanak decides.KeeperHub lands it.No strategycode changes.

Almanak's execution layer is three abstract classes: sign, simulate, submit. This package implements all three against KeeperHub, so every Almanak strategy, unmodified, dry-runs through KeeperHub, is signed in its enclave, broadcasts with one idempotency key per intent, and gets a verified receipt back. No private key on the machine.

03 / The problem

A clean execution layer,and one way to execute.

Almanak is an open-source DeFi strategy framework: 46 protocol connectors, an AI agent, and an execution layer built as three abstract classes so other backends could plug in. None ever did. What ships is a local key, the public mempool, and a retry that can pay twice. Their own repository records the result: on Arbitrum, a mint that had landed was retried after a nonce error and minted a duplicate position nobody tracked.
03 / The problem · 1 of 3

The private key lives on the strategy machine

The signer is a local key. Whoever reaches the box, or its environment, can sign anything the strategy could.

With KeeperHub: no key anywhere on the machine. The org wallet signs in Turnkey's enclave, behind KeeperHub's caps and policies; the package holds an API key with a scope.
1
03 / The problem · 2 of 3

The public mempool is the only submitter

The private-relay submitter is a stub that rejects every transaction, and the simulator is off on live networks. Nothing dry-runs the exact bundle before it goes out.

With KeeperHub: the exact compiled calldata is dry-run first, so a revert stops the tick before anything is signed; then it is broadcast through KeeperHub's RPC pool with sponsored gas.
2
03 / The problem · 3 of 3

No idempotency: a retry can pay twice

Almanak assigns a fresh nonce per attempt and retries on a nonce error. That is the duplicate mint in nonce_recovery.py.

With KeeperHub: one idempotency key per intent. A retry of landed work replays the first execution: 50 of 50 retries replayed, 10 of 10 crashed processes resumed, zero double broadcasts.

    05 / The guard

    An exit decision can be staleby the time it executes.

    Almanak decides to leave a vault on a snapshot. Between the decision and the broadcast the position can change: the keeper compounded, another process redeemed, a retry replays an exit that landed. So the redeem is never a bare write. Two shapes, both KeeperHub's.

    check-and-execute direct execution

    KeeperHub reads balanceOf(wallet) itself right before the write and runs redeem(shares) only if the balance still covers the decision. A stale decision comes back executed: false with the observed balance; nothing is broadcast. almanak-keeperhub exit, /exit on the phone.

    a workflow with a Condition node KeeperHub's engine

    The same decision in KeeperHub's own builder: a Manual trigger carries the shares, a balance node reads the vault, a Condition compares, and the Morpho redeem sits behind the true branch. A stale decision stops after three of four nodes. almanak-keeperhub exit-guard, /guard on the phone; workflow zhanaalz8k47rrjspihct.

    Both ran on production on 22 September 2026: the stale decision (5,000,001 against 5,000,000 held) stopped at the Condition in 3.7 s with nothing broadcast; the live one redeemed and verified in 8.4 s. The first scheduled exit taught the other lesson: a key made of (vault, wallet, shares) replayed an older redeem, so the key now carries the decision id, and the guard is what prevents a double redeem.

    09 / Authority

    Who can act,and through which gate.

    A retry of landed work carries the same key, so KeeperHub replays the first execution instead of sending again: 50 of 50 retries replayed, 10 of 10 processes killed after broadcast resumed, zero double broadcasts. The full model, including what a stolen API key cannot do, is in SECURITY.md.

    10 / Surfaces

    Three ways to use it,one truth.

    CLI

    For the strategy operator. almanak-keeperhub run --once runs any Almanak strategy through KeeperHub; exit is the guarded redeem as check-and-execute, exit-guard the same guard as a KeeperHub workflow; verify asks KeeperHub for its verdict on any hash.

    MCP server

    For any agent: Claude, Cursor, an n8n AI Agent. Read and dry-run by default; --write adds the real tick and both exits, the same split as KeeperHub's own mcp:read and mcp:write keys. Three real Claude sessions, recorded unedited.

    Telegram bot

    For the operator's phone: status, executions, verify, a dry run, a confirmed real tick, both guarded exits, and every failure-mode demo. It is what the demo video shows.

    All three read the same receipts file and drive the same code, so they cannot disagree about what happened. Two of the surfaces are KeeperHub's own: the compounder and the guarded exit are workflows this package generates from the strategy config and creates in KeeperHub's builder, where its engine runs them with no Almanak process at all (workflows 7cloybpqfrjvjv756dd2r and zhanaalz8k47rrjspihct).

almanak-keeperhub api-features --chain base_sepolia
# which of the two merged upstream features production has today
