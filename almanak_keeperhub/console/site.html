KeeperHub as the execution backend of a live DeFi strategy framework

Almanak decides.
KeeperHub lands it.
No strategy code changes.

Almanak's execution layer is three abstract classes: sign, simulate, submit. This package implements all three against KeeperHub, so every Almanak strategy, unmodified, dry-runs through KeeperHub, is signed in its enclave, broadcasts with one idempotency key per intent, and gets a verified receipt back. No private key on the machine. Everything below is read from files a real run wrote.

Judged on what goes wrong

Seven failure modes, on purpose

Each one is a script anyone can run against KeeperHub; the verdicts below are what they recorded.

Authority

Who can act, and through which gate

A retry of landed work carries the same key, so KeeperHub replays the first execution instead of sending again: 50 of 50 retries replayed, 10 of 10 processes killed after broadcast resumed, zero double broadcasts. The full model, including what a stolen API key cannot do, is in SECURITY.md.

Surfaces

Three ways to use it, one truth

CLI

For the strategy operator. almanak-keeperhub run --once runs any Almanak strategy through KeeperHub; exit is the guarded redeem as check-and-execute, exit-guard the same guard as a KeeperHub workflow with a Condition node; verify asks KeeperHub for its verdict on any hash.

MCP server

For any agent: Claude, Cursor, an n8n AI Agent. Read and dry-run by default; --write adds the real tick and the exit, the same split as KeeperHub's own mcp:read and mcp:write keys. Three real Claude sessions, recorded unedited.

Telegram bot

For the operator's phone: status, executions, verify, a dry run, a confirmed real tick, the guarded exit, and every failure-mode demo. It is what the demo video shows.

All three read the same receipts file and drive the same code, so they cannot disagree about what happened. Two of the surfaces are KeeperHub's own: the compounder and the guarded exit are workflows this package generates from the strategy config and creates in KeeperHub's builder, where its engine runs them with no Almanak process at all (workflows 7cloybpqfrjvjv756dd2r and zhanaalz8k47rrjspihct).

What this project fixed in KeeperHub, it now uses

The client speaks the merged shapes and latches to the old ones from the API's own answer; the first two merged changes went live on production on 16 September, the third followed on 22 September, and the runner's next tick used them without a change here. Verify it yourself

Nothing here asks to be believed

pip install 'almanak-keeperhub[mcp]'
export KEEPERHUB_API_KEY=kh_...        # your own KeeperHub key

almanak-keeperhub verify <hash or execution id>
# KeeperHub's verdict, the receipt, and who acted, decoded from the events

almanak-keeperhub api-features --chain base_sepolia
# which of the two merged upstream features production has today
